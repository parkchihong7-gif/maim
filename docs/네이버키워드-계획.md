## 2. 도톨이 AI 분석 요약 (설치하지 않고 공개 문서로 분석)
- 정체: Windows용 설치형 프로그램. Python 3.12 + PySide6(Qt) 화면, Kiwi 형태소 분석, SQLite, 내장 Chromium. AI는 **OpenAI Codex 실행기**(ChatGPT 계정 로그인 사용, 기본 모델 GPT 계열)로 연결한다. 네이버 API는 사용자 본인 키를 쓴다.
- 흐름: 연결 설정 → 내 블로그 스타일 진단 → 키워드 탐색·트렌드·벤치마킹 → 키워드 보관 → 준비 자료 승인 → 초안 → 최종 검수 → 복사

- 무료 배포가 가능한 이유: 서버가 없고 **각 사용자가 자기 AI 계정과 네이버 키를 쓰기 때문**에 제작자 비용이 0원이다.
- 비공개 부분: 작성 원칙, 키워드 점수 기준, 프롬프트 → **복제하지 않고 maim 자체 규칙으로 대신한다.**

## 1. 작업·배포 방식 — "모아서 한 번 배포" 가능 여부

**가능하다. 단, 반드시 새 브랜치에서 작업한다.**

- maim은 **브랜치가 하나뿐**(`claude/great-brown-j376u0`)이다. 체험 서버 배포(`git pull`)와 판매 고객 설치가 모두 이 브랜치를 본다고 봐야 한다. 이 브랜치에 작업 중인 코드를 올리면 **누가 배포하거나 설치할 때 반쯤 된 기능이 나간다.**
- 흐름:
  1. 새 브랜치 `claude/naver-keywords`를 만든다. 단계마다 커밋하고 push한다(저장만 하고 배포는 하지 않음).
  2. 단계마다 로컬에서 `npm run build`와 `tests/*.ts`를 통과시킨다.
  3. 끝나면 기본 브랜치에 합친다 → 사장님이 **체험 서버에 한 번 배포**한다. 체험 서버의 주인 자리가 판매용 고객 자리와 같은 조건이라서 시험대로 쓸 수 있다.
  4. 확인되면 판매 문서를 갱신하고 고객에게 업데이트를 안내한다.
- 되돌리기: Cloud Run 이전 리비전으로 트래픽을 돌리면 된다. 새 표 `keyword_pool`은 옛 코드가 쓰지 않으므로 DB가 깨지지 않는다.
- Windows에서 작업한다면 `for f in tests/*.ts`, `fuser`는 bash 명령이므로 PowerShell에서는 아래처럼 쓴다.
  - 시험: `Get-ChildItem tests\*.ts | % { npx tsx $_.FullName }`
  - 끄기: `Get-NetTCPConnection -LocalPort 8793 | % { Stop-Process -Id $_.OwningProcess }`

## 3. 서버 변경 (코드 지도 기준)

### 3-3. DB
- **`src/db/migrations/012_keyword_pool.sql`** (새 표라서 CREATE TABLE을 SQL 파일로 만든다)
```sql
CREATE TABLE IF NOT EXISTS keyword_pool (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  owner_key TEXT NOT NULL DEFAULT '',
  category_id INTEGER NOT NULL REFERENCES categories(id) ON DELETE CASCADE,
  keyword TEXT NOT NULL,
  pc INTEGER, mobile INTEGER, comp TEXT,          -- 검색광고: 월간 검색량, 경쟁 정도(낮음/중간/높음)
  doc_total INTEGER,                               -- 블로그 검색 total
  score REAL,
  top_json TEXT,                                   -- 상위 10개 글 [{title,desc,date}]
  status TEXT NOT NULL DEFAULT 'candidate',        -- candidate / used / hold
  fetched_at TEXT, used_at TEXT,
  UNIQUE(owner_key, category_id, keyword)
);
CREATE INDEX IF NOT EXISTS idx_kp_cat ON keyword_pool(owner_key, category_id, status, score);
```
- `categories`에 `칸붙이기()`로 `kw_refreshed_at`, `kw_error`를 추가한다(ALTER는 SQL 파일에 쓰지 않는다).

### 3-4. 갱신 로직 `src/pipeline/키워드갱신.ts`
1. **씨앗:** 카테고리 `name` + `topic_keyword` + `must_keywords`(최대 5개, 중복과 공백 제거). 씨앗이 없으면 건너뛰고 `kw_error`를 기록한다.
2. 검색광고 API → 연관 키워드. **거르기:** `exclude_keywords` 포함 단어 제거, 월간 검색량(pc+mobile) 100 미만 제거, 씨앗 낱말을 하나도 포함하지 않은 것은 감점.
3. 검색량 상위 50개 → 블로그 검색 API로 `total`과 상위 10개 글을 수집한다.
4. **점수(초기식, 배포 후 조정):**
   `점수 = log10(검색량) × 경쟁가중(낮음 1.2 / 중간 1.0 / 높음 0.8) × 포화가중`
   `포화도 = 문서 수 ÷ 검색량` → 포화가중: ≤5는 1.3, ≤20은 1.0, ≤50은 0.7, 그 이상은 0.4
5. 상위 **30개**를 저장한다. `kw_refreshed_at = 지금`.
6. 최근 제목(`listRecentTitles`)에 이미 쓴 키워드는 `used`로 둔다.

### 3-5. 매일 작업 `scheduler/dailyJob.ts`

## 0. "동일하게"의 범위 (중요)

설치 파일을 실행하지 않고 파악한 근거는 도톨이가 공개한 문서(README, 릴리스 노트, 데이터 안내, 오픈소스 목록)와 유튜브 영상 제목, GitHub 배포 페이지다.

| 구분 | 파악 정도 | 이 안에서 다루는 방식 |
|---|---|---|
| 기능 목록, 사용 순서, 화면 흐름 | ✅ 공개 문서로 충분 | **똑같이 만든다** |
| 기술 구성(Python·Qt·Kiwi·SQLite·Codex·네이버 API) | ✅ 오픈소스 목록으로 확인 | maim 기술(Node 서버)로 **바꿔서** 만든다 |
| 작성 원칙, 키워드 점수 기준, 프롬프트 | ❌ 실행 파일 안에 있는 비공개 자료 | **maim 자체 규칙**(제목규칙·검색노출규칙)과 B안 점수식으로 대신한다 |

- 설치해도 화면에 보이는 것만 더 알 수 있다. 실행 파일을 뜯어서 비공개 원칙을 꺼내 쓰는 것은 제작자 권리를 침해할 소지가 있으므로 **하지 않는다.**
- 그래서 A안은 "도톨이를 복제"하는 것이 아니라, **"도톨이와 같은 기능과 흐름을 maim 방식으로 만드는 것"**이다.
- 데스크톱 프로그램(설치형)으로 만들지 않는다. maim은 서버 방식이 맞다(판매용 자체 설치, 06:00 자동 생성, 휴대폰 사용).

## 2. 단계 (B안 1~5 다음에 이어서)

> B-1 ~ B-5는 `B_3번_수정안.md`를 따른다. 아래는 A안에서 추가되는 단계다. 각 단계는 새 브랜치에서 커밋하고, 배포는 마지막에 한 번 한다.

### A-6. 트렌드 관측 (데이터랩)
- **네이버 개발자센터 앱 하나에 "데이터랩(검색어트렌드)" 사용을 추가**하면 블로그 검색 API와 같은 Client ID/Secret을 쓸 수 있다(새 키 불필요).
- 새 파일 `src/naver/데이터랩.ts`: `POST /v1/datalab/search`, 기간 최근 12개월, 월 단위. 키워드 묶음은 최대 5개씩.
- `keyword_pool`에 `trend`(상승/보합/하락), `trend_json`(12개월 값)을 `칸붙이기()`로 추가한다.
- 점수에 트렌드 가중을 더한다: 상승 ×1.15, 하락 ×0.9.
- 🔎 화면에 작은 막대(12칸)를 표시한다. 예약 순서 `schedule_order`에 `trend`(상승 키워드가 있는 카테고리 먼저)를 추가한다.
- 갱신 주기는 1개월(B안과 같음).

### A-7. 내 블로그 스타일 진단 + 경쟁 블로그 벤치마킹
- 새 파일 `src/naver/블로그RSS.ts`: `https://rss.blog.naver.com/<아이디>.xml`에서 최근 글 20개(제목, 요약, 날짜)를 읽는다. 공개 RSS를 읽는 것이며, 로그인이나 자동 발행과는 무관하다.
- **스타일 진단:** 관리자 설정 "2) 블로그 주제"에 [내 블로그 진단] 단추를 둔다 → AI 1회 호출(도구 없음) → 말투, 문장 길이, 소제목 방식, 이모지 사용, 자주 쓰는 주제를 표로 보여 준다 → [이 스타일로 프리셋 만들기]를 누르면 `custom_` 프리셋이 생기고, 기존 프리셋 체계를 그대로 쓴다.
- **경쟁 블로그 벤치마킹:** 🔎 화면에 [블로그 벤치마킹]을 둔다 → 블로그 아이디 입력 → 최근 제목들에서 자주 나오는 낱말을 센다 → 검색광고 API로 검색량을 붙인다 → 보관함 후보에 추가한다(출처 `bench`).
- 저장: `seat_settings` 키 `style_diagnosis`(JSON, 진단일), 보관함 `source` 칸(`seed`/`bench`/`manual`).

### A-8. 준비 자료 승인 + 글 구성 선택
- **글 구성 4종:** 정보형 / 후기형 / 비교형 / Q&A형. 카테고리 폼에 ⑦ 칸 "글 구성"(기본 = 자동)을 추가하고, `directives.ts`의 sectionCount·오프닝 배정과 함께 `promptBuilder`에 구성별 소제목 틀을 준다.
- **준비 자료 승인(수동 생성에만):**
  - [지금 생성] 옆에 [준비부터 보기]를 둔다 → 조사 단계(`조사하기()`)와 키워드 데이터, **소제목 목록 초안**(AI 1회, 짧게)만 먼저 만든다 → 창에 표시한다(조사 요약, 메인·연관 키워드, 소제목 3~5개, 상위 글 패턴).
  - 사용자가 소제목을 고치거나 빼고 [승인하고 쓰기]를 누르면 → 그 자료로 글쓰기 단계만 실행한다(조사는 다시 하지 않음).
  - posts 상태에 `prepared`를 추가하고, `prep_json` 칸을 `칸붙이기()`로 추가한다.
  - **06:00 자동 생성은 지금처럼 승인 없이** 바로 초안을 만든다(사람 검수는 발행 전에 하므로 maim 규칙의 "사람 검수 3단계"를 지킨다).
- 시간: 준비 60~120초 + 글쓰기 300초. 한 번에 하던 5분이 둘로 나뉘므로 상태칸 문구를 맞춘다.

### A-9. AI 최종 검수 + 이미지 프롬프트 복사
- 포스팅 카드에 [AI 검수]를 둔다(수동, 주인만) → 완성 글을 AI가 점검한다(도구 없음, 90초): ① 근거 없는 숫자나 날짜 ② 금지 문구(cash-flow `shared/banned_phrases.py` 목록을 maim에 복사해 둔 것) ③ 메인 키워드 횟수와 위치 ④ 어색한 문장 3개. 결과는 **표시만** 하고 자동으로 고치지 않는다.
- [이미지 프롬프트 복사]: 제목·소제목으로 영어 프롬프트 3개를 만들어 클립보드에 복사한다(서버에서 이미지를 만들지 않음). **사장님이 허락할 때만** 넣는다.

### A-10. 백업·사용법
- 관리자 설정 맨 아래에 [작업 자료 내려받기](주인만) → `getDb().backup()` 스냅샷을 내려받는다. 키는 비밀값이므로 빼고 내보낸다.
- 📖 사용법에 "네이버 키 발급 → 키워드 보관함 → 트렌드 → 스타일 진단 → 준비 승인" 단계를 추가한다.

## 3. A안 vs B안

| | B안(수정안) | A안(동일 구성) |
|---|---|---|
| 내용 | 네이버 키워드 + 보관함 + 상위 글 + 매일 작업 연결 | B안 + 트렌드 + 스타일 진단 + 벤치마킹 + 준비 승인 + 글 구성 + AI 검수 + 백업 |
| 단계 수 | 5 | 10 |
| 새 API 키 | 검색 API 1세트 + 검색광고 1세트 | 같음(데이터랩은 검색 API 앱에 사용만 추가) |
| 글 1편 시간 | 지금과 같음(약 5분) | 자동은 같음. 수동 승인을 쓰면 +1~2분, AI 검수 +1분 |
| 위험 | 작음 | 화면이 많아져 초보 고객에게 복잡할 수 있음 |
| **권장** | **먼저 한다** | B안을 배포해 효과를 본 뒤, 필요한 단계만 골라서 |
